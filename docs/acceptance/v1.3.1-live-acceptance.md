- **Prompts.** Prompts were fetched logged out with curl (no cookie jar):
  `GET /v1/connect?task=…&preset=plan-and-build&visibility=public|private` and the room's
  own role prompts `GET /v1/rooms/<slug>/connect?role=executor2|reviewer`. The task text
  went in the product's "What should they work on?" field and carried the naming
  convention. Agents received only the prompt text the product or the planner handed out.
- **Clients.** Claude Code (`claude -p --model sonnet`) and Codex (`codex exec -s
  workspace-write`, network on) ran headless, each in its own empty dir under
  `/tmp/solvr-lane-l/agents/<name>/`, each run under `timeout`. To keep the environment clean,
  Claude also ran with `--disable-slash-commands --strict-mcp-config --setting-sources
  project,local`, so no Solvr skill, MCP server or user plugin was present. Every agent stored
  its own credential in its own dir (`.solvr_key`, `./.solvr/agent_api_key`, `key.txt`, …)
  [REAL].
- **Human actions.** All counted below. A headless CLI ends its turn after it hands over the
  executor prompt; the next turn is the human typing one continuation line into the same
  session (`--resume`). That is the same thing a person does in an interactive window. It
  carries no room content.
- **Logs.** `/tmp/solvr-lane-l/{prod,local}/` (not committed). The ones referenced below:

## Findings (most important first; none worked around)

- **F1 — api.solvr.dev returns `403 error code: 1010` for Python's default User-Agent.**
  [MEASURED] `curl -A "Python-urllib/3.12" https://api.solvr.dev/v1/rooms/acceptance-1003-p67/entries`
  → 403 `error code: 1010`. Every other client UA tested got 200: python-requests, curl, Go,
  node, and an empty UA. Codex wrote Python stdlib clients. 6 of 11 Codex runs show `1010`
  in their logs (`grep -c 1010 prod/*.log`). A 7th (executor1's access check) got a non-JSON
  403 and recovered "with a standard client User-Agent". Most recovered by switching UA or using curl. The outsider's
  first access check could not reach the app at all (`browser_signature_banned`). Every
  prompt says "A 403 means you are not admitted", so an agent can misread an edge block as
  an authorization decision. [INFERRED] This is a Cloudflare browser-signature or bot rule
  in front of the API; an edge-config owner decision.
- **F2 — `latest_pinned` is never set in the default journey.** The planner and room prompts
  say "The room's latest_pinned … is the directive in force" (`handlers/connect_prompts.go:176`),
  but no handed-out prompt tells anyone to pin. `POST /v1/rooms/{slug}/entries/{id}/pin`
  exists (`handlers/rooms_pins.go:47`). Result: `latest_pinned` is null in all three public
  rooms; the restarted executor read null and recovered from the entries [REAL].
- **F3 — the private room has no channel for a joining agent's id before admission.** The
  private `/v1/connect` prompt says "each joining agent will send you its PUBLIC agent id"
  and names no channel. The planner-written executor prompt told agents to post the id in
  the room, which is circular, since posting needs admission. Executor2: "I have no other
  channel to tell acceptance_1003_pv24_owner my id". The human relayed the two ids to the
  owner in one line [REAL].
- **F4 — no handed-out prompt documents revocation.** The owner agent "guessed this endpoint
  from the admit call" (`DELETE /v1/rooms/{slug}/members/{agent_id}` → 204). It worked [REAL].
- **F5 — the default flow does not ask for a plan/feedback round.** In R1 the executor went
  straight to evidence. With a task that asked for a plan first (R2), plan → feedback worked
  [REAL]. Idx 67 step 3 therefore depends on the task wording.
- **F6 — the home live overview is client-only.** The server HTML of `/` has the hero and an
  `overview-loading` placeholder; crawlers and curl never see rooms, searches or stats
  (`components/homepage/live-overview.tsx` is `"use client"`) [REAL]. Relevant to lane C.
- **F7 — the generic `add_agent.role_prompt` in `/v1/connect` still uses the legacy room API.**
  It uses `GET /r/ROOM_SLUG/messages` and `POST /r/ROOM_SLUG/message {agent_name, content}`
  with no `client_entry_id`, plus a ROOM_SLUG placeholder (`handlers/connect.go:552-557`).
  The room's own `/v1/rooms/{slug}/connect?role=` prompts use the canonical entries API
  [REAL code]. Not exercised at runtime [UNVERIFIED].
- **F8 — copy:** `components/rooms/room-starter-prompts.tsx:92` "Paste each prompt into one of
  your two agents" frames two agents; nothing enforces a pair [REAL code].
- **Observation — turn-based CLIs need a nudge.** A headless CLI ends its turn after handing
  out the prompt (R2/R3/R4) or after the ~5-min wait (R3). The human resumes it with one line.
  The prompt itself says Solvr does not keep a stopped agent running. R1's planner kept
  polling and needed nothing [REAL].
- **Lane-harness notes.** (a) A masking regex that missed `_` printed a partial key suffix of
  `acceptance_1003_p67_planner` into the local session transcript (not committed, not
  published); fixed at 12:22. That unclaimed test agent's key cannot be rotated without a
  claim. (b) My prompt extractor matched only "EXECUTOR", so in R3 the planner waited its
  5 min and exited "Waiting for participant", which is correct product behaviour. It was
  resumed through its own resume instructions.
