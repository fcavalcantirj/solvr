2026-09-21 — TASK 13 (operations): Restrict operator analytics and growth
             reports to explicit administrative access
================================================================================

WHAT THE TASK IS ABOUT

  Solvr measures two different things. PRODUCT ACTIVITY is published (tasks
  5-12 built that, and handlers/public_overview_allowlist.go decides exactly
  what reaches a visitor). OPERATOR ANALYTICS is the other one: traffic,
  acquisition, retention, cost, raw diagnostics and growth planning — the
  reporting Solvr does about ITSELF. That belongs to the people who run the
  product, and to nobody else.

  Two dangers, both server-side:
    1. ACCESS. A credential the product issues — a human account, an agent API
       key, a user key, a room owner, a room-scoped token — is a credential for
       USING Solvr, not for reading Solvr's own numbers. Hiding a link is not
       access control; the rule has to hold for somebody typing the URL.
    2. CACHING. An operator report a shared cache may store can be handed to
       the next visitor who asks for the same URL. A public overview request
       must never be able to hit an entry an operator's request created.

WHAT WAS THERE ALREADY, AND WHAT WAS NOT

  [REAL] Every /admin handler already checked X-Admin-API-Key itself, in THREE
      hand-rolled copies (admin.go checkAdminAuth, search_analytics.go
      checkSearchAnalyticsAuth, incidents_admin.go checkIncidentAdminAuth),
      each comparing the key with != (not constant time).
  [REAL] NOT ONE of them set a cache header. A GET /admin/search-analytics/
      trending answered 200 with no Cache-Control at all, which a CDN or proxy
      is free to cache heuristically. That was the real gap this task closes.
  [REAL] No GA4 or Search Console integration exists in the backend at all
      (grep over internal/ and cmd/): there are no credentials to leak there.
      The frontend carries the COLLECTION side only — the gtag measurement id
      in app/layout.tsx and sendGAEvent calls in lib/analytics.ts. A
      measurement id runs in every visitor's browser by design; it is not a
      credential, and a test that flagged it would only teach the suite to lie.
